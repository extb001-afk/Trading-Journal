# 로트(취득 묶음) 방식 — 설계

← [기능 · 원가 계산 방식](FEATURES.md#원가--손익-계산-방식)

> **설계 문서예요 — 방식 선택은 아직 코드에 없어요.** 지금 tj-bot 은 이동평균 하나로만 계산해요(아래 '지금'). 2026-10-30 (2판)부터 원가 장부가 취득 묶음(로트)을 함께 기록하고 '묶음 합 = 원가 칸'을 늘 확인하지만, 숫자는 이동평균 그대로예요.
> 기본값은 지금과 같게(이동평균) 두므로, 넣은 뒤에도 설정을 바꾸지 않으면 숫자는 그대로예요.

## 지금 — 이동평균

- 원가 장부(`src/accounting_basis.py`)는 묶음(자산 그룹 · 거래소는 거래소·코인마다)마다 **원가 아는 수량 · 원가 모르는 수량 · 남은 원가 합**만 들고 있어요.
- 사면 `acquire(묶음, 수량, 원가, 시각, 출처, 원가 모르는 수량)`(안 쓰는 칸은 None — 0 을 더하지 않아요), 원가만 더하는 자리(수수료·가스 원가화 · 수량이 먼저 들어온 승계 원가)는 `capitalize(묶음, 원가, 시각, 출처)`, 팔거나 보내면 `release(묶음, 아는 수량, 원가, 모르는 수량)`, 원가 모르던 수량에 값이 붙으면 `convert` — 원가 칸이 바뀌는 길은 이 넷뿐이고(옛 한 칸 쓰기는 장부 밖 호출 0), 뗄 원가는 늘 `평단 × 수량`이에요. 2026-10-30 (2판)부터 장부가 묶음마다 취득 로트(수량·원가·취득 시각·원장 출처)를 함께 기록하고, 처분은 모든 로트에서 같은 비율로 빼요(이동평균과 같은 결과 · 리플레이 끝에 '로트 합 = 원가 칸'을 확인).
- 그래서 선입선출·후입선출·개별 지정 같은 방식은 지금 계산할 수 없어요. [Beancount 내보내기](FEATURES.md#fava로-열기--beancount-내보내기)는 계정별 선입선출 로트를 내보내기 도구가 따로 골라 적어요(tj-bot 숫자와는 별개).

## 넣을 자료 구조

```python
@dataclass
class Lot:
    qty: Decimal            # 남은 수량
    unit_cost: Decimal      # 개당 원가(USD) — 원가 모름 = None(0 으로 지어내지 않음)
    acquired_ts: int        # 취득 시각(epoch 초) — 이동으로 옮겨도 그대로
    unit_cost_krw: Decimal  # 개당 원화 원가(원화 표의 규칙 그대로 · 없으면 None)
    src: int                # 원장 출처(posting_id — 리플레이가 읽는 행에는 source_kind 가 없어 행 번호로 · 같은 출처 두 번 = 정정 분기)
```

- 묶음마다 로트 목록을 들고, `acquire` 는 로트 하나를 더해요. 이동(내 지갑·거래소 사이)은 보낸 쪽에서 뗀 로트를 **취득 시각·원가 그대로** 받는 쪽에 옮겨요.
- 원가 모르는 수량도 로트(`unit_cost = None`)로 들고, 지금처럼 원가 아는 수량부터 떼는 규칙은 방식과 따로 둬요(원가 미확인 매도 = 지금 그대로 '원가 미확인').

## 방식(Booking) 인터페이스

```python
class Booking:
    def pick(self, lots: list[Lot], qty: Decimal, ctx) -> list[tuple[Lot, Decimal]]:
        """뗄 로트와 수량 — 합 = qty(모자라면 있는 만큼 · 나머지는 부르는 쪽이 원가 미확인으로)"""
```

| 방식 | 고르는 순서 |
|---|---|
| `Average`(기본 · 지금과 같음) | 로트를 고르지 않고 평단 × 수량(모든 로트에서 같은 비율로 뗌) |
| `Fifo` | 먼저 산 로트부터 |
| `Lifo` | 나중에 산 로트부터 |
| `Hifo` | 개당 원가가 높은 로트부터 |
| `Specific` | 사용자가 매도마다 고른 로트(지정 없으면 `Fifo`) |

- `release` 가 방식에게 뗄 로트를 묻고, 그 로트 원가 합이 실현 손익의 원가가 돼요. 리플레이의 나머지(이동 승계·수수료·명세)는 `acquire`·`release` 뒤에서 바뀌지 않아요.
- 원가 지문 시험(원장 → 원가·손익 골든)은 `Average` 에서 지금과 한 자리도 다르면 안 돼요.

## 설정

```json
"accounting": {"booking": {"exchange": "average", "onchain": "average"}}
```

- 묶음 종류별(거래소 보유 · 온체인 보유) 방식 · 기본 = 둘 다 `average`(지금과 같음) · 바꾸면 다음 리플레이부터 지난 숫자도 새 방식으로 다시 계산(원장 무변).
- 거래소와 온체인 방식이 다를 때 그 사이 이동은 로트를 그대로 옮기고, 떼는 순서만 받은 쪽 방식을 따라요.

## 명세 열

- 양도차익 명세에 **취득일**(뗀 로트의 취득 시각 · 여러 로트면 가장 이른 날 + '외 N') · **로트**(로트 수) · **방식**(`이동평균` · `선입선출` …) 열을 더해요.
- `Average` 에서는 취득일 = 비움 · 로트 = 비움 · 방식 = `이동평균`(지금 명세와 같은 숫자).

## 교과서 예(시험 값)

1 BTC 를 $10,000 에, 1 BTC 를 $20,000 에 산 뒤 1 BTC 를 $30,000 에 팔면:

| 방식 | 뗀 원가 | 실현 손익 | 남은 1 BTC 원가 |
|---|---|---|---|
| `Average` | $15,000 | $15,000 | $15,000 |
| `Fifo` | $10,000 | $20,000 | $20,000 |
| `Lifo` | $20,000 | $10,000 | $10,000 |
| `Hifo` | $20,000 | $10,000 | $10,000 |

- 방식마다 이 표 그대로인지 + `Average` 에서 기존 골든 무변인지가 첫 시험이에요.

## 세법 적용은 원문 확인 뒤

- 국내 가상자산 과세(시행 예정)의 취득가액 산정 방법(거래소·온체인별 이동평균·선입선출 등)은 **소득세법 시행령 원문을 확인한 뒤에만** 기본값으로 바꿔요.
- 그 전까지는 설정으로 고르는 참고 계산이고, 실제 신고는 거래소 공식 내역과 세무 전문가 확인을 따르세요.
